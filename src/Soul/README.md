# Soul challenge

Owned Dustweave module, promoted from the Inventory Battle research implementation. The planner and the C++ battle model are maintained by this project. It uses no Python process or research-directory paths at runtime.

Client preparation uses the shared structural binding resolver. `soul-binding-contract.json` describes required native roles; `trace-binding-contract.json` is separate so optional detailed trace failures do not disable the challenge. Both contain interface descriptions and one-way hashes, not client code. Compiler-side token lookups and runtime reflection strings use the same resolved names. A new client MVID rebuilds bindings instead of rejecting the version; the completed payload still pins the exact current client before loading.

Live runs export the installed client's current Soul tables through the shipped read-only table utility. The cache includes both assembly and database hashes, validates every table and regenerates corrupt entries. Embedded tables remain offline calibration inputs, never a fallback for unreadable live rules. Full rule fingerprints guard decision plans. Only the two audited animation-only fields (`IBEffectConfigTable.useAnimation` and `IBUnitItemTable.coolTimeUseAnimation`) may change without discarding existing candidate seeds; numeric, layout, cost or trigger changes invalidate them. Current tables still drive every simulation. Missing rule resources ask the user to finish the game update and retry.

The desktop entry and verification entry both use `SoulSession`. Explicit **Start all five** challenges all five native dungeons, including native rechallenges of historical clears. **Resume game progress** instead reads the current season from the server, skips already cleared dungeons and prioritizes an active dungeon, including a manual rechallenge. It works without a local tool record and incorporates manual progress made after a pause. Native Back/Enter navigation preserves the run; Resume never calls GiveUp or resets inventory, deck, coins or lives. An active battle is observed without another Start command. Completed game chapters are not fabricated battle wins in the tool's statistics. The game remains responsible for battle execution, rewards and transaction outcomes.

Search respects the actual shop, owned items, gold and per-account upgrade limits. Whole-dungeon growth routes are candidate seeds, not grants of ownership. `NativeDecisionSearch` searches complete economic/placement bundles. At most three independent worker kernels use fixed search seeds; `NativeDecisionPortfolio` compares their candidates on the same 512 combat seeds. Neither search seeds nor policy weights depend on battle outcomes. An unconfirmed purchase, upgrade or battle is never automatically repeated.

The simulation win-rate target is a search target, not a stop condition. Each dungeon now has a saved candidate-attempt target: 1,000, 3,000, 10,000 or 30,000 (initially 10,000 for dungeon four and 3,000 for the other dungeons). The target applies to each planning pass, including after shop refreshes and acquisitions; it is not a time limit or a count of unique legal boards. Finite capacity exploration and final validation are additional work. Three fixed search branches split the target, regardless of the performance setting. Low usage runs one branch with serial combat batches; balanced runs at most two branches with four-seed native batches; high performance retains three branches and the original unrestricted native batches (up to 16 native workers per branch). High performance adds no throttling. CPU availability can reduce concurrent search branches, never their number or candidate targets. Pauses are checked between native batches; an in-flight native batch completes cooperatively. The finite acquired-only fallback and independent 512-seed final audit remain intact.

Settings are stored in `tools/soul/settings.json`, normalized individually and snapshotted at the next planning pass. Missing or damaged settings use defaults without blocking progress. The panel saves automatically and collapses when a run starts, keeping progress visible; users may reopen it during a run. **Resume game progress** is the primary action; explicitly starting all five remains secondary. An offline comparison is available through `--soul-search-check <isolated-output>`: it uses the owned embedded model and synthetic table-based state, never a game connection or account credentials.

`SoulShopPolicy` continues seeking affordable improvements without a two-refresh cap. A statistically separated current improvement can be acquired before discarding its shop; the actual inventory is then read and replanned. Refreshing retains buying power for an observed offer, not an arbitrary terminal cash reserve. This reference is not a prediction of the next shop. Every continuing iteration must spend positive, receipt-confirmed coins. If no further funded improvement search is available, `best_available` uses the independently sampled legal plan with its measured risk unchanged and the remaining native lives. Confirmed exhaustion retries the same dungeon. Battle outcomes never train weights or alter search seeds.

Before discarding a weak shop, the planner compares its complete improvement with a separately searched acquired-only board on common combat seeds. It may secure the complete improvement when the sampled win-rate bounds separate and both the purchase and another funded shop are affordable. Otherwise it either keeps that measured improvement for battle or continues shopping while retaining buying power. It does not buy arbitrary pieces of a failed plan or use an unobserved future floor as placement space. The earlier `SoulReservePolicy`/catalog append implementations are retained only for offline comparisons; the live session does not call them. Every continue step has a positive confirmed cost, so unchanged inventory cannot cause an endless free planning loop. Pause is checked between iterations and transactions.

`NativeDecisionActions` interleaves upgrades, equipment assignment, substitutions, coupled floor/roster additions and spatial moves. Actual equipment bindings survive compatible moves/upgrades. Removed owners release only their own equipment. Every socket is checked against the native scalar encoding, including off-board/ambiguous positions. A state is expanded once; local enumeration is not restarted repeatedly around an unchanged winner. The complete layout is simulated before its purchase path is produced. No catalog-based unverified reserve is appended after choosing a winner.

Growth potential participates in candidate retention, alongside a separate current-wave champion. It probes upcoming enemies using only the proposed acquired bundle and a feasible upgrade budget. Finalists additionally compare three consecutive future waves with prefix-funded upgrade branches and a finite-lives dynamic-programming recurrence. This is conditional acquired-roster evidence, not an unconditional campaign-clear probability: future shops and rearrangements are not known. Independent current-wave audits still constrain growth comparisons. Empty-cell effects, stamina competition and enemy reactions can make extra units harmful, so unit count alone is not the objective. The UI displays the current search phase, evaluated candidate count and elapsed time, then the purchase/upgrade count, cost, remaining coins and sampled win rate. Below-target attempts stay visibly identified. In fixed-candidate mode at every performance level, one candidate source retains the established randomized search with its reserve append disabled; new action search and explicit expansion provide the other candidates. All candidates, including the acquired-only fallback, compete under the same independent combat audit. Offline benchmarks retain the original full search for comparison.

Pause stops planning promptly, or waits for an already submitted economic operation/battle to settle. The tool does not close the game. The shared control lease is held for the full run and the prior connection component is restored afterwards.

After the game confirms that the current dungeon's lives are exhausted, the campaign returns through the native result screen and re-enters that same dungeon. Earlier clears are retained. A persisted defeat can resume without double-counting its attempt, and an unresolved battle never authorizes a restart. Cumulative battle/transition counts do not impose a separate retry limit; the user can pause. Attempt counters are display/journal data only. Search seeds, combat rules and ranking weights do not depend on the previous battle outcome or the number of failed attempts; every decision evaluates the currently observed game state. Algorithm changes are assessed separately with offline replay.

Shop purchases update the existing slot in place and immediately create the purchased item's native storage view with its normal drop animation. Upgrades update that same view and play the native level-up effect. The native drag-purchase display helper creates a replacement slot and is unsuitable for direct purchases. Full shop reads/rebuilds are not repeated after purchases, upgrades or ordinary wave entry. The board rebuilds only after a confirmed layout save. A native pool recovery removes identifiable orphan shop views from earlier runs; it does not change owned items or server state. Final layout checks require one view per owned item and one view per shop slot before battle. A fresh start exits and abandons only the current idle dungeon through its verified native confirmation, then starts dungeon one; resume preserves the current challenge.

Selling uses the native storage removal and pool return, so a sold item disappears immediately. Odd-price refunds follow the server's positive half-up rounding, while execution reconciles the accepted item-specific receipt with the wallet instead of treating an extra refunded coin as failure. Upgrade rendering preserves the view's DTO when a previous reconciliation replaced the inventory DTO list; the native updater updates both references.

Confirmed purchases and upgrades retain a short 350 ms presentation interval before the next action or final layout save, so native storage and upgrade animations remain visible even on fast responses. This adds no shop reload or network request.

Selling follows the native `SellSelectedItem` path. Its accepted server response removes the item and updates `InventoryBattleManager.CurrentGold`, but leaves `IbPlayDBInfo.Coin` unchanged. After verifying the receipt's item identity and actual refund, a local synchronization command requires the same run, removed item and matching native wallet before updating that stale cached coin value. It sends no extra main/item/deck/shop requests and never replays a sale. Unknown or rejected outcomes still pause. Diagnostic export prioritizes Soul status, campaign, bounded timeline and error files so unrelated daily history cannot evict the failure report.

The embedded model has calibrated rule evidence, not a client-version gate. Runtime source resolves validated interface roles and compiles against the installed client. Current rule tables are exported from that client and database; both input hashes identify their cache. Candidate-library evidence is reused only for unchanged decision rules (the two audited presentation-only animation fields are excluded). Changed decision values invalidate that library. A compiled payload must match its actual running client, and optional trace bindings cannot disable normal play. Obsolete APIs are removed rather than retained as old-client runtime branches.

`assets/bd2_inventory_battle.dll` is the calibrated portable x64 model, SHA-256 `ABE5030CB23ECCADEBED5504A51989CD6348BD58CDE493E779703082E46F40DB`. Its owned source is in `native/`. `native/build.ps1 -Output <file>` builds a candidate using g++; it does not silently replace the validated artifact. Rebuilding requires combat parity validation, updating the route catalog model fingerprint, and updating the explicit source-integrity check. No processor-specific instruction target or fast-math is enabled.

The compressed route catalog contains item/layout growth routes only. Account captures, credentials, protocol recordings and private research evidence are not distributed.
