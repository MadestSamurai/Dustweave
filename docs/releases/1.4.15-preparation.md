# 1.4.15 local acceptance and publication preparation

Historical preparation record. Publication subsequently completed; see [the deployment receipt](1.4.15-deployment.md).

Prepared on 2026-10-21. **Not published.** Source changes are local; no GitHub release or OTA index was changed by this task. Published 1.4.14 is unchanged.

## Delivered behavior

- Existing supported clients approve one update, install `1.4.15-bridge.1`, and automatically continue to final `1.4.15`. No second download-size or restart approval is needed. The bridge does not initialize game connections, daily automation or schedules.
- Final 1.4.15 supports updates to the launcher, runtime and managed components. Delta failure on overwritten or damaged files falls back to signed file-block reconstruction.
- The native root entry can offer repair without a functioning application CLR. Critical startup files are checked before loading the CLR; the independent repair helper is pinned and recoverable. Accounts, settings, plugins and unowned files are retained.
- Interrupted preparation resumes from verified data. Replacement journals support recovery and startup-failure rollback. A failed final startup restores the bridge without an automatic retry loop.

## Evidence

- `final/release.json`, `final/validation-scope.json`: canonical packaged source, localization, binary and real UI/tool gates. The final update scope passed 429 checks. The full synthetic baseline passed 5,784 checks across 118 groups; unchanged application checks were reused rather than rerun for every native-entry correction.
- `acceptance-passed/results.json`: nine actual two-stage/fault scenarios using original 1.4.7 and 1.4.14 helpers in both editions; final startup rollback; recovery before replacing the entry and after replacing it with a broken Portable runtime. Summary aliases in this file are not additional test executions.
- `native-repair-release-proof/results.json`: both editions repaired damaged startup/helper/descriptor files after a single confirmation. Portable also lacked hostfxr; Lite contained foreign overlaid runtime files. Every owned target file and account/plugin sentinels were checked.
- `patch-acceptance/results.json`: both actual v3 deltas reconstructed all 221 Lite / 677 Portable files with exact hashes.
- `bridge-first-stage-final/results.json`: original 1.4.14 helpers independently passed the bridge upgrade, startup failure and interrupted recovery gates.
- `publisher-final-tests.log`: 136 publisher checks, including separate indexes, signed larger v3 patches, repair inventory prerequisites and required native repair evidence. `publisher-final-linux/` is the corresponding deployment candidate.
- `release-acceptance.json`: combined final publication evidence and exact full-package digests. The first-stage publication uses `bridge-first-stage-final/results.json`.

These are isolated local process tests using signed, prepared cached payloads. Transport corruption, resume and fallback are separately covered by synthetic tests. They are not a physical power-cut test or a live CDN publication check. No game operations were performed.

Two packaged defects found during this task were fixed before accepting the candidate: invalid launcher IL could terminate the CLR before a repair prompt, and the native entry lacked the Common Controls v6 declaration required by its repair progress window. Earlier `delivery*` folders and failed repair directories are superseded experiments, not release candidates.

## Prepared publication inputs

- Final: `final/updates.json` (schema 4), `capable-site/updates-v3.json`, two v3 patches, and canonical signed inventories/blocks in `repair-final/`.
- Legacy entry: `bridge-v2/updates.json` (schema 3), `legacy-site/updates.json`, twenty v2 patches, and canonical inventories/blocks in `acceptance-passed/bridge-repair/`.
- Preserve these canonical signed repair envelopes and pass their directories through `publish-update-signed.ps1 -RepairDirectory`. Do not upload separately re-signed copies of the same immutable manifest.

Before activation, deploy the capability-aware publisher and exact no-cache nginx rule. Publish and verify both sets of repair files, publish the final capable index, then expose the legacy bridge index last. Use `-Capable` only for the capable lane. The server rejects a bridge whose final target or matching inventory is absent. Keep the old v1 lane untouched.

GitHub publication, server deployment, cloud uploads and public download verification remain separate authorized release actions. The future update workflow reads the capable index; it does not repeatedly depend on downloading an internal bridge from GitHub.

Publisher/workflow/test-proof documentation was finalized after the application package build; no packaged application source changed afterward. The client packages above are the same bytes used in the final acceptance.

## Limits

If the root executable itself is missing, use the independent helper or restore the official package. Lite still requires the Windows .NET Desktop Runtime. A broken legacy installation that cannot run its original updater cannot acquire new capabilities without first restoring that installation. During a disconnected bridge preparation, reopen Dustweave after connectivity returns to continue.
