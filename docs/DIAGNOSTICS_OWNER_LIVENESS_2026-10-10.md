# 控制窗口误报退出与诊断导出修复

## 结论

已复现并修复一个会让仍在运行的控制程序被判定为退出的缺陷。游戏使用的 Mono 在无法获得较高进程访问权限时，`Process.GetProcessById` 会抛出“找不到进程”的 `ArgumentException`。原代码将这种异常直接解释为 `suite.owner-exited`，回收日常组件的执行权。因此，重复点击连接也会重复失败。

两份反馈包属于同类故障，发生时间不同，不能当作同一次会话拼接。原记录没有保存被检查的控制进程 PID、启动时间或 Windows 错误码，无法确定这两次用户现场究竟是哪种权限配置导致查询失败。修复解决的是已经通过真实客户端运行时复现的错误判定，不把某款安全软件、管理员启动或隔离多开当作已证实的根因。

## 证据

| 来源 | 可确认内容 | 缺失内容 |
|---|---|---|
| 原始日志包 | 01:52:18 的连接操作失败，调用经过功能启用和账号核对；显示旧的通用会话停止提示 | 不能用组件基线版本推断主程序版本；缺少底层进程查询证据 |
| 1.1.1-beta 一键导出包 | 主程序 08:42:50 启动，08:42:58 功能启用被 `suite.owner-exited` 暂停；并非游戏观察连接完全丢失 | 控制程序 PID、启动时间、查询错误码以及连续的连接切换历史 |
| 隔离复现 | 仅限制测试子进程自身的访问权限，旧 Mono 查询报“找不到进程”，Windows 最小权限查询仍确认存活 | 不改变用户应用、游戏进程或系统安全策略 |

游戏状态观察连接和取得自动操作执行权是两层状态。诊断页面显示“连接正常”，同时最近一次操作失败，二者可以同时成立。

## 修复

- 使用 `OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION)`、`GetProcessTimes`、`GetExitCodeProcess` 检查存活与启动时间，避免 Mono 的高权限进程查询。
- 明确区分不存在、已经退出、同 PID 被另一进程占用、无法读取。权限不足保留 `suite.owner-unreadable` 和 Win32 错误码，不解释成退出。
- 保留真正退出后的停止保护、启动时间校验和待结算操作保护，不自动重复有消耗的操作。
- 功能启用请求和运行时状态切换记录双方进程身份、查询结果和组件指纹。记录不含模块二进制载荷；只在切换时写入，单文件 512 KiB，最多保留三个历史文件，并纳入日志清理。

## 一键导出审计

原一键导出约 4 MB，已经保留关键错误和调用栈；原始目录压缩包约 802 MB，没有必要让用户再次提供整个目录。但原导出仍不足以独立判断本次误报的底层原因。

已补充：

1. `run-error.json`、连接与兼容性元数据、队列初始化结果。
2. 控制权请求与切换历史、顶层日志和诊断日志的已知轮转文件。
3. 连接和错误证据优先于大量步骤快照；每个来源单独计算扫描预算，避免主程序日志挤掉其他工具。
4. 超过 8 MiB 的文本日志保留最多末尾 2 MiB，从完整行开始脱敏；清单标注原始大小与截断状态。结构化 JSON 不截成无效片段。
5. 清单新增各来源的证据覆盖情况。没有跳过文件仅表示所选文件成功读取，不再隐含“现场完整”。摘要同时列出最近一次历史操作失败，与当前连接状态分开。
6. 嵌套账号库、设置、原始命令和二进制继续排除，敏感字段脱敏。新增记录留在本机，由用户自行选择是否导出和发送。

仍有边界：导出为最近七天的有界快照；被用户清理、尚未产生、文件锁定、超出容量或扫描预算的证据不能恢复。覆盖清单和跳过原因用于明确这些边界，不作完整现场保证。

## 验证

- `UnifiedSuite`、`SuiteOwnerProbe`、`DiagnosticExport`、`LogCleanup`：113 项通过。
- 使用安装客户端的 Mono 运行时在独立进程进行对照：受限但允许最小查询的测试进程，旧实现误判、新实现返回 alive；完全拒绝查询时，新实现返回 unreadable / Windows error 5。
- 回归覆盖真实退出、PID 启动时间变化、待结算时暂停、身份恢复后重新启用、诊断写入失败不阻断执行、日志轮转、导出预算优先级和脱敏。
- 源码边界检查通过；连接组件使用当前安装客户端的接口成功编译。未启动或连接游戏，未修改用户游戏进程；用户机器上的最终修复效果仍需新版实用验证。

本次修复纳入 1.1.2-beta，既有 1.1.1-beta 安装包不会自动包含这些修改。打包验收进一步通过 2,718 项检查及双版本成品检查；发布状态以对应版本的发行记录为准。
