### 本次修正的验收问题

账号菜单的 `Closed` 事件在 WPF 关闭动画结束后才触发，原测试仅等一次 Dispatcher 空闲就检查，导致误报。现改为有上限地等待 `Closed`，并检查定位属性的本地覆盖已清除，而不是要求 WPF 的有效 `PlacementTarget` 永远为 null。产品菜单逻辑未被放宽。

补充了行右键按下的选中对象、队列勾选不变、表头/空白不保留行上下文，以及按钮菜单关闭后键盘菜单打开的测试。鼠标释放通过 WPF 的实际指针命中对象触发菜单，不能只用合成 `MouseUp` 事件替代；因此不将合成事件测试宣称为物理鼠标定位验收。

## 五、简体中文原文同时充当查找键的情况

> 本节保留重构前的发现及当时的修改约束。2026-11-03 的架构调整已解除主要界面的原文反查依赖，当前规则与验证结果见第六节；不要再按本节建议从新文案重建别名，或为同名文本合并不同语义的键。

### 机制

1. **反向索引（`DailyLanguage` 构造函数）。** 4 个文本文件共 3,279 条，其中 3,046 条的简体中文不含 `{`。程序把这些简体中文「原文 → 键」建成 `sourceKeys`。`L.Translate(原文)` 的查找顺序：先当作键查；查不到就按简体中文原文查 `sourceKeys`；再查不到，就用带参数的通知模板做正则匹配；最后查工具消息表。全部落空时**原样返回中文原文**。
2. **代码里直接写中文、再查译文。** 走这条路的入口有：
   - `DailyPreferencesPanel` 的 `Stage`（32 处）、`Check`（44 处）、`Row`（10 处）、`Note`（3 处）、`LocalButton`（2 处）。例如 `Stage(income, "经营一键领取", …)` 经 `Label` → `L.Literal` → `Translate("经营一键领取")`，才找到 `prefs.business` 的繁中和英文。
   - 另有 `L.Literal` 4 处、`L.Translate("中文")` 9 处、`Describe("中文")` 2 处。
3. **Core 发出的中文消息。** Core、Connection、Runtime 里约 381 处 `Report(…)` / `Exception(…)` 直接使用中文。Desktop 端靠反向索引和 `notices.json` 的 51 个带参数模板翻译这些消息；模板的正则就是从简体中文（或 `source` 字段）生成的。
4. **`Core/Localization/Messages.zh-CN.txt`（961 行，`代码=中文`）。** 它必须与 `runtime.json` 中 `message.<代码>` 的简体中文**逐字相同**，冒烟测试会检查（`Runtime source translation drift`）。
5. **已保存的历史记录。** 队列记录和回执保存的是当时的中文显示文本。改名之后，旧记录仍带着旧文本，所以 `DailyLanguage` 里已经有一张别名表（例如 `"镜中免费战斗" → stage.mirror`），`WorkStep` 也会按旧文本回退查找。

### 改错的后果

不会报错，界面上也不会崩溃，而是**悄悄退化**：

- 简体中文用户看起来一切正常，因为看到的就是原文；
- 繁中 / 英文用户在这些位置会看到简体中文；
- 现有冒烟测试大多通过 `L.Get(键)` 取期望值，抓不到这类问题。

### 本仓库里的具体例子

- **只改 JSON，不改代码。** 把 `prefs.business` 的简体中文从「经营一键领取」改成「经营与餐厅」，而 `Stage(income, "经营一键领取")` 不动：繁中和英文界面会显示简体「经营一键领取」。
- **两边都改了，也可能出错。** 「经营与餐厅」已经是 `stage.management` 的简体中文。两个键的中文相同，反向索引只保留**先出现的那个键**，于是设置页可能显示成「Business and restaurant」，而不是原来的「Claim business income」。
- **按钮名被提示原文引用。** 「接续原队列」出现在 7 条 JSON 文本（`run.resume`、`run.resume_footer`、`run.recovery_body`、`issue.action.*` 等）和 1 条 Core 消息中，还是 `DailyRunPanel.cs` 的默认文字。只把按钮改成「继续上次进度」，其他提示就会叫用户去点一个已经不存在的按钮。Core 那条消息还受 `Messages.zh-CN.txt` 与 `runtime.json` 逐字一致的约束；加上 `接续` 在 `Messages.zh-CN.txt` 中出现 25 次，统一用词必须 Core 和 Desktop 一起改。
- **历史记录。** 改掉 `stage.*` 的简体中文后，旧记录中的旧名称需要加进别名表，否则繁中和英文用户查看旧记录时会看到中文原文。

### 什么样的文本可以放心改

同时满足以下四条：

1. 只通过 `L.Get` / `L.Text` / `L.Bind(键)` / `{l:Tr 键}` 读取；
2. 不是 `message.*` / `notice.*`，也不对应 `Messages.zh-CN.txt` 中的行；
3. 旧的简体中文没有在任何 `.cs` / `.txt` / 测试中按原文出现，也没有被其他文案用「」引用；
4. 新的简体中文不和其他键的简体中文重复。

本次第一批就是按这四条逐键核对后修改的（核对脚本用法见第一批实施记录的「已做的检查」）。

### 后续批次的建议做法

- **E13 命名统一**：同时修改调用处的中文字面量和 JSON；如果新名称与已有键重复，就直接改用那个键，不要新建同名键；把旧名称加入别名表。
- **E1 用词统一**：先决定术语（例如「任务」「继续上次进度」），再一次性修改 Desktop 的 JSON、`Messages.zh-CN.txt`、Core 中对应的中文消息、按钮默认文字和测试；旧说法进入别名表；改完后运行 `Runtime source translation drift` 检查和全量冒烟。
- **长期**：把 `DailyPreferencesPanel` 的中文字面量改为直接传键，并在测试中加一条检查——找不到译文的中文原文出现在繁中 / 英文界面时报错。这样以后改简体中文就不会悄悄影响其他语言。

## 六、本地化架构调整 — 2026-11-03

本次落实第五节的架构建议，保留已有界面设计。调整范围是文案标识、分类、消息呈现及开发期检查，不改变游戏操作、账号凭证、任务选择或恢复判据。

- **界面使用明确的键。** 日常设置、跑商计划表头及账号对话框不再把中文原文反查成键。设置分类按固定键、工具分类按 `CategoryId` 判断；表格字段与显示标题分离。三语搜索独立取资源值。不同含义即使中文相同也保留各自的键，例如关闭窗口与关闭开关；`prefs.business` 的领取收益与 `stage.management` 的经营汇总不能因为改名而合并。
- **当前翻译不能改写兼容规则。** `LocalizedTextCatalog` 负责资源、格式参数和缺失文案检查。删除从当前简体中文值自动构造反向表的逻辑；旧消息映射固定在 `legacy-inputs.json`，51 个旧动态模板保留明确的 `source`。改中文、调整 JSON 顺序或出现同名文本均不改变这些映射。旧中文键改为固定标识，旧名称只留在兼容入口。
- **新消息使用标识和参数。** `DailyText` 传递键、参数和原始诊断后备文字；账号检查进度已接入。已注册 Core 消息优先按消息代码取译文，取消 Core 原文与界面中文必须逐字相同的约束。尚未结构化的既有运行消息通过固定适配层显示；不借这次重构修改它们的行为或回执格式。新动态消息不再依赖中文正则解析。

### Windows 复查及自动保存调整 — 2026-11-05

- 按用户追加要求，日常设置取消保存按钮，改为当前账号自动保存；输入停止 500 毫秒后写入有效设置，页眉显示等待、已保存或未能保存。默认补药策略不变。
- 账号切换、执行任务与正常关闭沿用 `SavePending`，在延迟保存之前立即离开也不会漏掉有效修改。关闭内置工具的退出路径也先处理待保存设置。
- 无效／未完成的数字不会覆盖文件；后台校验不抢焦点、不滚动页面。保存先构造独立候选，后面的字段校验失败也不会部分改写内存策略；修正后自动继续保存。
- 补药入口携带任务账号；另一个账号有无效输入时保留并定位该输入，不误高亮另一账号的补药开关。执行中遵守现有设置锁，结束后入口可用。临时高亮补偿边距，避免内容跳动。
- 更新搜索冒烟预期：英文 “Weekly NPC quests” 同时匹配任务及补药条件说明是正确结果，不再错误要求只能返回一个卡片。
- 本地化冒烟用真正未完成的输入检查草稿保留；有效编辑应自动保存，不能再用“永不写入有效草稿”作为旧验收要求。
